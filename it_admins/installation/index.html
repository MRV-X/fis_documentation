    Installation und Betrieb

    Diese Seite beschreibt die Neuinstallation Schritt für Schritt, danach die Aktualisierung einer bestehenden Installation und den Betrieb. Die Reihenfolge ist wichtig, besonders bei den Schritten 7 bis 10.

    Überblick

    Schritt Was Wo
    1 Voraussetzungen prüfen Server
    2 Code holen, Umgebung anlegen, Pakete installieren Terminal
    3 Datenbank anlegen psql
    4 .env ausfüllen Datei
    5 Tabellen und Cache-Tabelle anlegen Terminal
    6 Superuser anlegen Terminal
    7 Anwendung starten und als Superuser anmelden Browser
    8 Erste Einrichtung anlegen Browser
    9 Standardrollen anlegen (seed_roles) Terminal
    10 Ersten Verwalter ohne Superuser-Rechte anlegen Browser
    11 Mailversand einrichten und testen Browser
    12 Stationen, Benutzer und Rollen anlegen Browser
    13 Zeitgesteuerte Aufgaben starten Terminal

    1. Voraussetzungen

    • Python 3.12
    • PostgreSQL 16 (die Anwendung läuft nur mit PostgreSQL)
    • Git
    • Ein Mailserver (SMTP), damit neue Benutzer ihren Passwort-Link per E-Mail bekommen. Ohne Mailserver geht der Betrieb trotzdem: Die Anwendung zeigt dann ein temporäres Passwort an (siehe Schritt 11).

    2. Code holen und Pakete installieren

    git clone https://github.com/MRV-X/FIS.git
cd FIS
python -m venv ../virt
../virt/Scripts/activate        # Linux: source ../virt/bin/activate
pip install -r requirements/base.txt      # Betrieb
# pip install -r requirements/dev.txt     # stattdessen für die Entwicklung (ruff, djlint, …)
    Datei Inhalt
    requirements/base.txt Betrieb
    requirements/dev.txt Betrieb + Entwicklung (ruff, djlint, …)
    requirements/docs.txt Dokumentation (MkDocs)

    3. Datenbank anlegen

    Benutzer und Datenbank werden mit psql angelegt (ersetzt das frühere Skript mydb.py):

    CREATE USER fis WITH PASSWORD 'sicheres-passwort';
CREATE DATABASE fisdatabase OWNER fis ENCODING 'UTF8';

    4. Datei .env ausfüllen

    Vorlage kopieren und anpassen:

    cp .env.example .env
    Eintrag Bedeutung
    SECRET_KEY Geheimer Schlüssel von Django. Neu erzeugen: python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
    FIELD_ENCRYPTION_KEY Schlüssel für verschlüsselte Felder (z. B. das E-Mail-Passwort). Neu erzeugen: python -c "import base64, os; print(base64.urlsafe_b64encode(os.urandom(32)).decode())"
    DATABASE_URL postgres://fis:sicheres-passwort@127.0.0.1:5432/fisdatabase (Benutzer, Passwort, Host, Datenbankname aus Schritt 3)
    ALLOWED_HOSTS Adressen, unter denen die Anwendung erreichbar ist
    SITE_URL Basisadresse für Links in E-Mails, z. B. https://fis.klinik.de (in Produktion Pflicht)

    Weitere Einträge (Sitzungssperre, Passwort-Mindestlänge, Proxy/HTTPS) stehen mit Erklärung in .env.example.

    Schlüssel nicht verlieren

    SECRET_KEY und FIELD_ENCRYPTION_KEY gehören nur in die .env (nie ins Git). Ohne FIELD_ENCRYPTION_KEY sind verschlüsselte Felder (z. B. das E-Mail-Passwort) nicht mehr lesbar. Den Schlüssel nach dem ersten Start nicht mehr ändern.

    Das gilt, solange es nur diesen einen Schlüssel gibt. Geplant ist eine Schlüsselrotation mit mehreren Schlüsseln (FIELD_ENCRYPTION_KEYS, siehe internal/konzepte/KONZEPT_ENCRYPTION.md). Danach ersetzt eine Anleitung diesen Hinweis. Bis dahin den Schlüssel nicht ersetzen und die Schlüssel getrennt vom Datenbank-Backup aufbewahren (internal/konzepte/KONZEPT_BACKUP.md).

    Entwicklung oder Produktion

    Welche Einstellungen gelten, bestimmt DJANGO_SETTINGS_MODULE. manage.py und Celery nutzen ohne Angabe FIS.settings.local (Debug an), wsgi.py und asgi.py nutzen FIS.settings.production. Im Betrieb die Variable auch für manage.py setzen: DJANGO_SETTINGS_MODULE=FIS.settings.production.

    5. Tabellen anlegen

    python manage.py migrate
python manage.py createcachetable
    • migrate legt alle Tabellen und die Rechte an.
    • createcachetable legt die Tabelle für den gemeinsamen Cache an (fis_cache). Der Schritt wird oft vergessen. Ohne ihn bricht das Anlegen eines Benutzers mit Temp-Passwort mit „Relation fis_cache existiert nicht“ ab.

    6. Superuser anlegen

    python manage.py createsuperuser

    Der Befehl fragt nach Benutzername, Anrede, Vor- und Nachname, Funktion, Abteilung, E-Mail, „Zugriff ab“ und Passwort.

    Wofür der Superuser gedacht ist

    Der Superuser richtet die Anwendung ein (Einrichtung, Rollen, erste Benutzer). Er sieht keine Patientendaten, und jede seiner Aktionen wird im Zugriffsprotokoll festgehalten (Aktion „Superuser-Aktion“). Für die tägliche Arbeit bekommt jede Person ein eigenes Konto mit Rollen (Schritt 10 und 12). Das Superuser-Passwort sicher aufbewahren und das Konto nicht gemeinsam nutzen.

    7. Anwendung starten und anmelden

    Entwicklung:

    python manage.py runserver

    Im Betrieb startet der Webserver (z. B. gunicorn/uvicorn hinter einem Proxy) FIS.wsgi bzw. FIS.asgi.

    Im Browser die Adresse aufrufen und mit dem Superuser anmelden. Solange es noch keine Einrichtung gibt, sind die meisten Seiten leer. Das ist normal.

    8. Erste Einrichtung anlegen

    1. Einstellungen (oben in der Leiste) → Klinik-Einstellungen öffnen. Ohne vorhandene Einrichtung zeigt die Seite ein leeres Formular.
    2. Name, Kürzel, Adresse und Kontaktdaten eintragen sowie die Fristen (Benutzer-Warnung und -Deaktivierung, Aufbewahrung der Protokolle, Dauer des Notfallzugriffs) prüfen.
    3. Das Klinikkürzel (kk) hat genau 6 Buchstaben oder Ziffern. Es kennzeichnet alle Datensätze der Einrichtung. Ein Kürzel einer später gelöschten Einrichtung wird nie wieder vergeben. Deshalb sorgfältig wählen.
    4. Speichern. Die Standard-Lockerungsstufen der Einrichtung werden automatisch angelegt.

    Weitere Einrichtungen legt später jemand mit dem Recht „Einrichtung anlegen“ an (Rolle „Einrichtungsverwaltung“); für sie entstehen die Standardrollen automatisch.

    9. Standardrollen anlegen

    Erst nach Schritt 8, einmalig je neuer Datenbank:

    python manage.py seed_roles

    Der Befehl legt die Rollen je vorhandener Einrichtung an. Die Ausgabe zeigt, was angelegt wurde:

    Einrichtung Testklinik:
  IT-Administration: angelegt, 6 Recht(e) ergänzt, 0 entfernt
  Benutzerverwaltung: angelegt, 5 Recht(e) ergänzt, 0 entfernt
  …

    Reihenfolge einhalten

    Läuft seed_roles, bevor es eine Einrichtung gibt, entstehen Rollen ohne Einrichtung. Solche Altrollen gelten als einrichtungsübergreifend und sind nicht gewollt (siehe internal/planung/Rechte-Plan.md, AP-09b). Gab es den Fehler schon, zuerst die Einrichtung anlegen und den Befehl danach noch einmal ausführen.

    Die Standardrollen:

    Rolle Zweck
    IT-Administration Einrichtung (Klinik-Einstellungen) und Stationen verwalten; kein Zugriff auf Fachdaten, Benutzer oder Rollen
    Einrichtungsverwaltung wie IT-Administration, darf zusätzlich weitere Einrichtungen anlegen
    Benutzerverwaltung Benutzer anlegen, bearbeiten, löschen, Passwort zurücksetzen und ihnen Rollen zuweisen; baut keine Rollen
    Rollenverwaltung Rollen aus beliebigen Rechten des Katalogs bauen; weist sie nicht zu
    • Die vier Rollen sind gesperrt: In der Rollenverwaltung lassen sich weder Name noch Rechte ändern, und sie können nicht gelöscht werden. Nur seed_roles legt sie an und setzt ihre Rechte.
    • Erneutes Ausführen setzt die Rechte dieser Rollen genau auf die Liste in user/roles.py: Fehlendes wird ergänzt, Überzähliges entfernt. Das ist nach einem Update nötig (siehe unten).
    • Alle weiteren Rollen (Pflege, Ärzte, Revision, …) legt die Klinik selbst mit der Rollenverwaltung an. Diese Rollen sind frei änderbar. Autorisiert wird immer über die Rechte der Rolle, nie über ihren Namen.
    • Aufgabentrennung: Wer Rollen baut (Rollenverwaltung), weist sie nicht zu. Wer Benutzer verwaltet (Benutzerverwaltung), baut keine Rollen. Beides darf nicht bei derselben Person liegen; die Anwendung lehnt eine solche Kombination ab. Die Rollenverwaltung darf jedes Recht in eigene Rollen aufnehmen, ohne es selbst zu besitzen. Details: internal/planung/RECHTE_UEBERSICHT.md.

    10. Ersten Verwalter anlegen

    Damit nicht dauerhaft mit dem Superuser gearbeitet wird:

    Damit die Aufgaben getrennt bleiben, legt der Superuser zwei Personen an, nicht eine:

    1. Benutzer → Benutzer anlegen. Daten eintragen, im Block der Einrichtung die Rolle Benutzerverwaltung wählen. Danach genauso eine zweite Person mit der Rolle Rollenverwaltung anlegen. Optional eine dritte mit IT-Administration oder Einrichtungsverwaltung.
    2. Hat die Person keine E-Mail-Adresse (oder wählen Sie „Temp-Passwort“), zeigt die Seite ein temporäres Passwort in einem Fenster an. Es erscheint nur dieses eine Mal: kopieren und der Person sicher übergeben. Nach dem Schließen geht es weiter (zur Bearbeiten-Seite des Benutzers, ohne dieses Recht zur Benutzerliste). Die Person muss das Passwort bei der ersten Anmeldung ändern (Flag „Passwort ändern“).
    3. Hat die Person eine E-Mail-Adresse, bekommt sie einen Link zum Festlegen des Passworts.
    4. Mit den neuen Konten anmelden und prüfen, dass Benutzerliste und Rollenverwaltung erreichbar sind.

    Wenn die E-Mail nicht gesendet werden kann

    Ist der Mailserver nicht erreichbar (oder noch nicht eingerichtet), legt die Anwendung den Benutzer trotzdem an, zeigt eine Warnung und erzeugt stattdessen ein temporäres Passwort.

    11. Mailversand einrichten und testen

    Einstellungen → Klinik-Einstellungen → Abschnitt „E-Mail-Versand“: Server, Port, Verschlüsselung (TLS, SSL oder keine), Benutzer und Passwort eintragen und die Test-E-Mail senden. Das Passwort wird verschlüsselt gespeichert (FIELD_ENCRYPTION_KEY). Ohne Eintrag versucht die Anwendung localhost:25.

    Die Links in den E-Mails beginnen mit SITE_URL aus der .env. Der Wert muss von außen erreichbar sein.

    12. Stationen, Benutzer und Rollen anlegen

    1. Einstellungen → Stationen: Stationen der Einrichtung anlegen.
    2. Benutzer → Benutzer anlegen: je Person die Rollen je Einrichtung wählen und die Stationen zuordnen, auf die sie zugreifen darf. Nur wer in der Einrichtung eine Rolle hat, kann dort Stationen haben.
    3. Rechte werden nur über Rollen vergeben. Direkt am Benutzer vergebene Rechte gibt es nicht mehr: Das Feld ist aus dem Django-Admin entfernt, und vorhandene direkte Rechte wirken nicht mehr.
    4. Die Benutzerverwaltung weist dem Benutzer vorhandene Rollen der Einrichtung zu. Die eigenen Rollen ändert niemand selbst. Eine Kombination, die Rollen bauen und Benutzer anlegen/bearbeiten erlaubt, wird abgelehnt.
    5. Ein Recht gilt nur in der Einrichtung, in der die Rolle zugewiesen ist. Wer in mehreren Einrichtungen arbeitet, bekommt dort jeweils eigene Rollen und wählt oben die aktive Einrichtung.
    6. Die Rollenverwaltung baut die Rollen der Klinik (zum Beispiel Pflege, Ärztlicher Dienst, Datenschutz/Revision mit den Rechten des Bereichs „Protokolle“, Leitung mit Zugriff auf alle Stationen). Dafür gibt es keine Standardrolle; die Rollenverwaltung kann jedes Recht des Katalogs aufnehmen, ohne es selbst zu besitzen.
    7. Die Benutzerverwaltung weist diese Rollen den Mitarbeitern zu.

    13. Zeitgesteuerte Aufgaben (Celery)

    Jeden Befehl in einem eigenen Terminal (oder als Dienst) starten:

    # Beat (Zeitplaner)
celery -A FIS beat -l info

# Worker (unter Windows)
celery -A FIS worker --pool=solo -l info

    Die Zeitpläne sind unter Serverzeitpläne beschrieben.

    Aktualisierung einer bestehenden Installation

    git pull
pip install -r requirements/base.txt
python manage.py migrate
python manage.py seed_roles
    • migrate führt neue Migrationen aus. Sie legen auch neue Rechte an.
    • seed_roles ergänzt die neuen Rechte in den Standardrollen (z. B. perm_settings_overview für die Einstellungs- übersicht). Eigene oder geänderte Rollen bekommen neue Rechte nicht automatisch: Diese in der Rollenverwaltung von Hand ergänzen. Ohne das Recht „Einstellungsübersicht öffnen“ kommen Nicht-Superuser nicht mehr auf die Seite Einstellungen.
    • Direkt am Benutzer vergebene Rechte (früher im Django-Admin) wirken nicht mehr. Wer solche Rechte hatte, braucht eine Rolle mit diesen Rechten und eine Zuweisung in der Einrichtung.
    • Wurde die Cache-Tabelle noch nicht angelegt: python manage.py createcachetable.
    • Die Migration user.0002_clear_user_groups leert die frühere Zuordnung von Benutzern zu Gruppen. Sie war nur eine Spiegelung der Mitgliedschaften; die Rollen je Einrichtung bleiben unverändert.

    Prüfen

    python manage.py check
python manage.py test

    Vor einem Push zusätzlich die Prüfungen aus der CI: ruff check ., ruff format --check . und python -m djlint templates/ --check.
